# Enumeration

We look at the open ports:

```bash
sudo nmap 10.129.3.232 -p- --min-rate 5000 -sS -Pn -n -oN ports
```

```console
Nmap scan report for 10.129.3.232
Host is up (0.19s latency).
Not shown: 65532 closed tcp ports (reset)
PORT      STATE SERVICE
22/tcp    open  ssh
80/tcp    open  http
54321/tcp open  unknown
```

Now we run a detailed scan against each port we found:

```bash
sudo nmap 10.129.3.232 -p22,80,54321 -sCV -T5 -vvv -oN Exact_scan
```

```console
PORT      STATE SERVICE REASON         VERSION
22/tcp    open  ssh     syn-ack ttl 63 OpenSSH 9.9p1 Ubuntu 3ubuntu3.2 (Ubuntu Linux; protocol 2.0)
80/tcp    open  http    syn-ack ttl 63 nginx 1.26.3 (Ubuntu)
|_http-title: Did not follow redirect to http://facts.htb/
54321/tcp open  http    syn-ack ttl 62 Golang net/http server (MinIO)
|_http-title: Did not follow redirect to http://10.129.3.232:9001
Service Info: OS: Linux; CPE: cpe:/o:linux:linux_kernel
```

As we can see in nmap, `|_http-title: Did not follow redirect to http://facts.htb/` means nmap couldn't resolve facts.htb, so we add it to `/etc/hosts`:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524090556.png)

There's a website, so we can do a quick enumeration with whatweb to see what we find:

```bash
whatweb http://10.129.4.18
```

```console
http://10.129.4.18 [302 Found] HTTPServer[Ubuntu Linux][nginx/1.26.3 (Ubuntu)], RedirectLocation[http://facts.htb/], Title[302 Found]
http://facts.htb/ [200 OK] Cookies[_factsapp_session], Email[contact@facts.htb], HTML5, HTTPServer[Ubuntu Linux][nginx/1.26.3], Title[facts]
```

We confirm we're facing an nginx server on a Linux machine. Now we can visit the site:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524091228.png)

Browsing the site we don't find a clear entry vector, so we look for alternative subdirectories by fuzzing the web:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524092020.png)

We find an interesting endpoint called "admin". Visiting it redirects us to `/admin/login`, where we find:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524092323.png)

Default credentials like `admin`/`admin` or `admin`/`1234` didn't work, so we can try creating an account and see what we find:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524092551.png)

It takes us to a panel that, as we can see at the very bottom, is based on the Chameleon CMS, version 2.9.0 (vulnerable):

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524092729.png)

Researching this version I found CVE-2025-2304:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524092923.png)

There's a vulnerability that lets us escalate our privileges from the test account to `admin`. Also, Chameleon has some relationship with AWS S3, meaning we can obtain privileged credentials to retrieve privileged files:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524131643.png)

Now our test account is an administrator. Let's log in with the new credentials `test`/`test`:

![](/Hacked-Machines/assets/images/Screenshot%202026-05-24%20141951.png)

First we configure aws s3:

```bash
aws s3 configure
```

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524145050.png)

Now we can see what's inside this server, specifically the endpoint the site pointed us to at `{IP}:54321`:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524145238.png)

What we see are the buckets. Let's go into "internal" and see what we find:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524145300.png)

The `.ssh` directory is important, since that's where SSH private/public keys are stored:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524151630.png)

The id_ed25519 file looks like a private key. Let's download it to our working directory using cp:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524151805.png)

Now we can use this private key. The question is: which user? When I researched the Chameleon CMS 2.9.0 vulnerabilities, I also found an LFI vulnerability, specifically in `/admin/media/download_private_file` with the `file=` parameter. This lets us retrieve `/etc/passwd` and pull the system users to test which one the private key works for:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524184527.png)

Reviewing the file we find 3 main users: (root, trivia, william).

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524184329.png)

Now we can try connecting over SSH. When we try to use the private key for the user trivia, it asks for the passphrase, which is basically a password that protects the private key:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524185017.png)

The best thing to do here is extract a hash from the passphrase in order to crack the password of the protected private key:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524190937.png)

Now we can crack it with john, which gives us the following password:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524191047.png)

Now we can connect over SSH using the private key and providing the passphrase `dragonballz`:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524191227.png)

We see we can run `/usr/bin/facter` as root using sudo:

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524191259.png)

I looked up facter in our old reliable [GTFOBins](https://gtfobins.org/gtfobins/facter/):

![](/Hacked-Machines/assets/images/Pasted%20image%2020260524193704.png)

As GTFOBins says, facter will execute the first `.rb` file it finds in the given path, and since we're running it with sudo, the Ruby code runs with administrative (root) privileges. So it's convenient to use a Ruby reverse shell, e.g. [here](https://github.com/secjohn/ruby-shells/blob/master/revshell.rb):
